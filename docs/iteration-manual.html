0开工前必须知道的四件事

① 本地源码现在就是唯一的源码，丢了就没了 服务器上只有一份「源码打包 zip」（_archives/ 里），而且是历史打包版本。 Windows / macOS 两端的本地代码是从线上已发布的 .exe / .dmg 里反向解包（app.asar）重建出来的，与线上运行版本一致 —— 这是目前最完整的桌面端副本。 安卓本地没有工程目录，源码仅以 _archives/LinkCoffee-android-source.zip（1.9）和 android-v1.9-legacy-src.zip 形式存在，需先解包才能改。

建议：立刻给 ~/teaching-system 建一个 git 仓库或打个压缩包备份。
② 安卓源码已恢复并出差距报告 本地安卓工程已从 _archives/LinkCoffee-android-source.zip 恢复为完整 Kotlin/Compose 工程（android/，versionCode=10 / 1.9），线上最新 APK 为 versionCode=27 / 1.26。 已用 jadx 反编译线上 v1.26 出差距报告 android/RECOVERY_AND_GAP.md，功能合并待 Android Studio 环境完成。详见 §2 与 §4。
③ 相对网站，客户端不用改业务代码 安卓 / Windows / macOS 三端都是「套壳」：业务逻辑（登录、云盘、社区、挑战、格式转换…）全部复用网站，通过同一套 /api/v1 或直接加载站点页面。 所以 90% 的日常迭代只改 Web 端，客户端只有「外壳 / 导航 / 版本」这点东西要动。别在三端各自重写一遍业务。
④ 两个坑位已经替你填好了
  • README 里引用的 tools/publish_app.py、verify.js、ssh_run.py 等工具在服务器下发的源码包里并不存在（打包脚本只挑了白名单文件）。本次已补写 ~/teaching-system/tools/publish_app.py，专门用来发布 mac / ios（后台版本管理页只有 android / windows / windows-portable 三个渠道）。
  • 网站后台的「版本管理」页没有 mac / ios 渠道，mac 只能走脚本发。
⑤ 生产库已经迁到 MySQL，本地开发仍用 SQLite 快照 线上（YOUR_SERVER_IP）自 2026-10-16 起数据库后端是 MySQL 8（见 §8），/opt/websystem/data/netlab.db 那个 SQLite 文件只是陈旧副本，对生产无效，别再用它改线上数据。 本地开发（server/data/netlab.db）仍是 SQLite 快照，结构与线上一致，改代码同步上线即可，数据库走独立通道。

安卓这个缺口为什么必须处理 服务端发布 APK 时会解析 APK 内部的真实 versionCode/versionName，与页面填写的对不上就直接拒收。 而客户端的更新判断是「versionCode 必须大于当前」。所以：
  • 如果直接拿本地这份 1.9 源码打包上传，会被服务端拒绝（内部是 10，页面填不出 27 以上）；
  • 就算强行把 versionCode 改成 28 发出去，手机端会更新成功，但界面会从 1.26 “倒退”回 1.9，丢掉 17 个版本的改动。

3Web 端：开发与上线

本地站点现在就在跑 已启动，地址 http://127.0.0.1:8000，用的是本地 SQLite 数据快照（结构与生产一致）。 注意：本地改的是 SQLite 快照，不会影响线上 MySQL 生产库。

3.1 启动 / 重启本地服务

cd ~/teaching-system/server
./run.sh                # → http://127.0.0.1:8000（改代码自动重载）
PORT=9000 ./run.sh      # 换端口

run.sh 干的事就是设环境变量再跑 wsgi.py：

export DATA_DIR="$HERE/data"          # 本地 SQLite 库与上传文件都在这（快照，与线上结构一致）
export SECRET_KEY="dev-secret-key-local-only"
export FLASK_ENV=development
exec .venv/bin/python app/wsgi.py    # debug=True，改完存盘即生效
想换一套数据做实验 把 DATA_DIR 指到别处即可，例如 DATA_DIR=/tmp/exp ./run.sh。db.py 首次启动会自动建表，不会污染生产快照。

3.3 推上线（改完本地确认无误后）

# ① 同步代码（排除缓存与备份文件）
rsync -av --delete \
  --exclude '__pycache__' --exclude '*.bak*' --exclude 'data/' \

  ~/teaching-system/server/app/ \
  root@YOUR_SERVER_IP:/opt/websystem/app/

# ①' 若 rsync 不方便，scp 也行（逐个目录）：

  ~/teaching-system/server/app/* \
  root@YOUR_SERVER_IP:/opt/websystem/app/

# ② 改属主并重启 Apache（mod_wsgi 只在重启时重载代码）
ssh -i ~/.ssh/teaching_system_deploy root@YOUR_SERVER_IP \
  "chown -R www-data:www-data /opt/websystem/app && systemctl restart apache2"

# ③ 验证
curl -s -o /dev/null -w "%{http_code}\n" https://your-server.example.com/
三条铁律 ① 只同步 app/，不要同步 data/（线上库现在是 MySQL，不同步本地 SQLite 也行，但习惯上别动）； ② 改完必须 chown www-data + systemctl restart apache2，否则不生效； ③ 动了数据库结构（db.py 建表 / 迁移），重启前先备份 MySQL：mysqldump -u admin -p netlab > netlab.bak-$(date +%Y%m%d-%H%M%S).sql。
本地 Python 3.13 vs 线上 3.10 — 写代码别用 3.11+ 语法 线上是 Python 3.10.12，tomllib、ExceptionGroup、typing.Self 等 3.11+ 特性会直接报错。 改完代码先在本地跑通，再同步；线上排查用 /opt/websystem/venv/bin/python -m py_compile。

3.4 改线上数据（MySQL 是生产库）

线上数据库是 MySQL 8（库 netlab，账号 admin，127.0.0.1:3306），后端由 /opt/websystem/db-backend.env 切换。这是唯一的生产库。

⚠️ 别再碰 /opt/websystem/data/netlab.db 那个 SQLite 文件是迁移前的陈旧副本，sqliteweb.service（:8081）现在只会编辑它，对生产（MySQL）完全无效。改线上数据请走下面两条路，别再用 db-live.sh 直连那个旧文件。

路线 A：网站后台（推荐）

登录网站 → 右上角「管理」→ 在后台里改课程、公告、激活码、用户等。带业务逻辑、有外键/级联保护，最安全。

路线 B：直连 MySQL

上服务器后用命令行；或本地做 SSH 端口转发再连：

# 服务器本机
mysql -u admin -p netlab

# 本地经 SSH 转发（端口别冲突时）
ssh -N -L 3306:127.0.0.1:3306 \
  -i ~/.ssh/teaching_system_deploy root@YOUR_SERVER_IP
mysql -h 127.0.0.1 -P 3306 -u admin -p netlab

需要写密码哈希（绕过业务直接改 users 表时）：python3 tools/pw-hash.py --sql 用户名 '明文'。

4安卓端：开发与打包

4.1 先决定走哪条路线（因为源码落后 17 版）

路线 A：从现有 1.9 源码继续（推荐）

  • 先把 _archives/LinkCoffee-android-source.zip 解到 android/android/；
  • 把 versionCode 直接跳到 28、versionName 写成 1.27，以 1.9 源码为基础往前开发；
  • 优点：源码是原始 Kotlin，改起来最舒服，工程结构完整；
  • 代价：1.10–1.26 那 17 版的界面改动会丢失，相当于回退到 1.9 的美术/交互；
  • 适合：那 17 版主要是小修小补，或者你本来就打算重做界面。

路线 B：从线上 1.26 的 APK 反编译

  • 用 jadx / apktool 解 v1.26 APK，拿到最接近线上的代码；
  • 优点：界面与线上一致，不会「倒退」；
  • 代价：Compose 的 Kotlin 代码反编译后可读性很差（大量合成函数名），基本只能当参照物，不能直接编译回去；
  • 适合：只是想确认 1.10–1.26 具体改了什么，再手工搬回路线 A 的源码里。
实操建议 走 路线 A，同时用路线 B 解一份 v1.26 放在旁边当「改动参照」。两件事我可以帮你做：① 把两端源码做一次结构级对比，列出 1.10–1.26 差在哪几个页面；② 直接帮你把 versionCode/versionName 改到 28/1.27。说一声就行。

4.2 打开工程（仅在选了路线 A 并已解包后）

  1. 用 Android Studio（不是 IntelliJ IDEA） File → Open
  2. 选中的是内层目录：~/teaching-system/android/android 不是最外层 android
  3. 首次 Gradle Sync 约 3–5 分钟（依赖走阿里云镜像，不用翻墙）
  4. 成功标志：底部 Gradle sync finished
重要：必须用 JDK 17 AGP 8.7.3 要求 JDK 17。gradle.properties 里已注释掉硬编码的 org.gradle.java.home（跨平台考虑）， 命令行脚本会自动探测；用 Android Studio 时要在 Settings → Build Tools → Gradle → Gradle JVM 里选 17。

#    android/android/app/build.gradle.kts

    versionCode = 28        // ★ 必须大于线上当前值 27

5Windows 端（Electron）

它不是「浏览器套个框」

是原生桌面外壳 + 站点实时内容：自绘标题栏/工具栏/侧边导航/状态栏，中间内容区是一个原生 WebContentsView，直接加载 https://your-server.example.com。 所以网站一改版，客户端内容自动跟着变，登录态、云盘、社区、挑战全都复用。

这意味着 绝大多数迭代只改网站；客户端只在「导航项 / 外壳观感 / 升级逻辑」上动。

5.1 源码结构

5.4 三个必须知道的坑（README 里踩过的真实问题）

坑 1 · 外壳布局塌陷

body 必须显式声明成 flex 列，否则隐藏侧栏后整个主体塌成 0 高、状态栏上移：

body { display: flex; flex-direction: column; }

坑 2 · 外壳画的浮层永远看不见

内容区是原生 WebContentsView，永远绘制在外壳 HTML 之上。任何 position:fixed 覆盖到内容区的下拉菜单都会被网页盖住，而且 DOM 断言查不出来（元素存在、尺寸正常，就是看不见）。
正确做法：菜单用系统原生菜单 Menu.popup()，更新对话框用独立无边框窗口 update.html。

坑 3 · 下载卡在 100% 不动

用 net.request() 下大文件时 res.on('end') 偶发不派发，文件其实已完整落盘。所以完成判定不能只靠 end，要额外用「已收字节数 ≥ 总字节数」+ 磁盘真实大小 + SHA-512 三重兜底。

7发布与 OTA 闭环

7.1 原理

客户端启动 8 秒后 / 运行中每 6 小时
        ↓
GET https://your-server.example.com/api/v1/app/version?platform=<渠道>&version_code=<当前>
        ↓
服务端查 app_versions 表里该 platform 的 is_latest=1 那行（MySQL）
        ↓
返回最新版本号 / 下载地址 / SHA-512 / 更新说明 + need_update
        ↓
客户端下载 → 校验 SHA-512 → 安装（Win 静默替换 / Mac 打开安装包 / 安卓 调起安装器）

7.2 版本号规则（关键，别填错）

渠道version_code 怎么来示例文件名约定
android用整数，人工填，必须 = build.gradle.kts 的 versionCode，且 > 线上 271.27 → 28teaching-system-v28.apk
windows由版本名自动推导 major×10⁶+minor×10³+patch1.4.9 → 1004009teaching-system-desktop-setup-v1004009.exe
windows-portable同上1.4.9 → 1004009teaching-system-desktop-portable-v1004009.exe
mac同上（三段式版本名）1.0.11 → 1000011LinkCoffee-mac-1.0.11-arm64.dmg

7.3 发布方式 A：网站后台（只有 android / windows / windows-portable 三种）

登录网站 → 右上角「管理」→ 顶部「版本管理」→ 选渠道、填版本号、上传安装包 → 发布。服务端会自动算 SHA-512、把同渠道旧记录降级成「历史」、把新记录标成「最新」。

7.4 发布方式 B：命令行脚本（推荐，且 mac / ios 只能用它）
